# Historical forecast calibration audit (rolling-beta-v1)

The authenticated and browser-local **Forecast Calibration Audit** screen compares a simple, predeclared rolling empirical directional probability against a constant 50% baseline. It is an evaluation tool, not a trade signal, broker feed, or evidence of positive net expectancy.

For each contiguous run of complete imported candles and each horizon `h = 1, 3, 12` bars, a forecast issued after the close of bar `i` estimates `P(close[i+h] > close[i])`. The model counts exactly `w` historical matured labels `y[k] = 1(close[k+h] > close[k])` for `k` from `i-h-w+1` through `i-h`. Every training label is fully known by bar `i` close. With `w` in 40, 100, 250 and Beta(1,1) smoothing, `p = (up + 1)/(w + 2)`. A forecast is scored only once bar `i+h` has closed. Flat closes are *not higher*.

The UI reports per-horizon sample count, mean Brier loss, 0.25 Brier of the 50% reference, Brier skill `1 - loss/0.25`, binary log loss, five-bin empirical calibration error and ten latest settled examples. Negative Brier skill is worse than the constant baseline. Positive in-sample skill is not proof of a tradable advantage; class imbalance, overlapping labels, model selection and serial dependence matter. No spread, slippage, commission, market impact, financing, contract value, stop/target or execution simulation is included. Brier scores cannot be converted to trading profits.

Source isolation: legacy imported CSV uses its dataset SHA-256 and exact instrument; private archive mode uses a ready single source-identified archive, verified SHA-256, and a bounded 20,000-bar read-only window. The audit refuses missing provenance, malformed OHLC, non-ascending timestamps and misaligned candles. Missing timestamps and partial aggregates split the data into separate runs, so no forecast spans an unobserved gap. Monthly/weekly/daily market-calendar assumptions are not implemented; only 1m/5m/15m/1H are supported. Archive bid-only candles are historical observations, not broker-executable asks. The public Pages version can only evaluate its browser-local imported CSV.

No model is fitted on an untouched future outcome. The deterministic tests check strict maturation, prefix invariance, gaps/partial aggregates, flat returns, insufficient sample reporting and malformed input. Run `cd frontend && npm test` and `npm run build`. This is an incremental step toward genuine forward paper-trading and independent calibration monitoring, neither of which is active yet.


## Forward-only forecast ledger core (not activated)

The new frontend/lib/forward-forecast-ledger.ts is a separately testable, **in-memory** building block for eventual prospective forecast journaling. Unlike the historical calibration audit, it accepts only sequential completed candles arriving within a configured maximum lag relative to a **trusted injected receipt clock**. Each feed has an exact instrument/provider/venue/source/price-side/timeframe identity; a different identity, revised bar, stale/future bar, backward clock, or retroactive forecast fails closed. Issued probabilities are immutable and idempotent by forecast ID and by model/bar/horizon. Horizons are fixed at 1, 3, and 12 completed bars. An outcome is scored only after the target bar is received; any missing intermediate candle voids pending outcomes rather than silently filling a gap. Brier and log loss are computed only from settled forecasts, and the 50% reference Brier is shown separately. The core never opens a trade.

**Not an enabled live feature:** There is no trusted authenticated provider adapter, server worker, database ledger, recovery, UI, durable event audit, or alert transport connected to this module. It must not be fed from imported historical archives and described as forward-tested. An injected clock alone cannot prove source authenticity or prevent a malicious caller from replaying fabricated data; actual prospective evidence requires a server-controlled receipt timestamp, authorized source, append-only durable journal and independently verifiable forward run. Feed market closures are currently treated conservatively as gaps. No real-world predictive performance, financial P&L or executable broker fill was measured. The separate quote-driven paper execution research in PR #18 is not integrated.

Run the new seven synthetic unit tests with: cd frontend && node --experimental-strip-types --test tests/forward-forecast-ledger.test.ts. Next: wire a verified authorized completed-candle feed to a durable idempotent server ledger, then connect calibration/drift alerts and paper-trade execution research without allowing retroactive forecasts. Do not enable live trading or claim profitability based on these tests.

## Historical score-stability review (fixed two-window comparison)

The Forecast Calibration Audit now displays a **descriptive** comparison of the last 100 matured evaluations against the immediately preceding 100 for each of the 1-, 3- and 12-bar horizons. Fewer than 200 settled historical evaluations produce `INSUFFICIENT`, not a fabricated stability result. The calculation reads only the selected source-isolated historical window, validates ordered issue/evaluation timestamps and exact horizon alignment, and does not change the source data.

The latest 200 matured evaluations must also form a **single uninterrupted, timeframe-aligned sequence**. If those evaluations cross a missing candle, partial aggregate, weekend closure or disconnected interval, the review returns `INSUFFICIENT` with no comparative scores rather than joining non-adjacent periods. Gaps entirely before the latest 200 evaluations do not invalidate that later contiguous comparison. Issue and evaluation timestamps must be aligned to the selected timeframe. This is conservative: it does not distinguish legitimate closures from feed outages. The historical calibration scores over separate contiguous segments are still shown independently; only the two-window stability comparison is suppressed when it would bridge a gap.

For each fixed window it reports Brier loss; a `REVIEW` flag appears if recent Brier is at least 0.02 higher than the preceding window or recent Brier is worse than the constant 50% baseline (0.25). These thresholds are **heuristic review prompts**, not statistical significance tests, calibrated control limits, proof of distribution drift or an automated alert. `NO_FLAG` means only that neither heuristic threshold was crossed; it is not proof of stability or trading edge. Consecutive h-bar directional outcomes overlap for h > 1, so the effective sample size may be much smaller than the displayed count. A regime shift or change in class balance can affect the scores. The model was already evaluated on this historical dataset; this review is not independent prospective validation.

The new pure `frontend/lib/forecast-stability.ts` module can later be reused for authentic forward outcomes, but there is still no verified provider feed, persistent server ledger, restart recovery or notification transport. It does not calculate executable P&L. Eleven synthetic regression tests cover insufficient samples, deterioration, improvement, prefix-causal evaluation, overlapping horizons, malformed data, immutability, gaps across the two comparison windows, recovery after an older gap and timestamp alignment. Run `cd frontend && node --experimental-strip-types --test tests/forecast-stability.test.ts`.


## Replay-validated forecast journal checkpoints (offline core, not activated)

`frontend/lib/forward-forecast-journal.ts` wraps the existing in-memory forward-only ledger with a bounded, versioned sequence of observed candle and forecast-issuance events. `checkpoint()` returns a detached, explicit `UNVERIFIED_LOCAL_EVENT_LOG` payload; `restore(checkpoint, trustedClock)` replays all events through the same causal ledger checks before accepting a restart. It rejects changed source identity, invalid event order, future-dated receipts, stale/revised candles, retroactive forecasts, duplicate journal events and malformed schemas. Identical candle/forecast retries do not duplicate entries. Pending 1/3/12-bar forecasts survive replay and settle only when later completed candles arrive. The log is capped at 50,000 events rather than silently dropping history.

This is **not durable persistence**: no server/database writes, crash-safe transactions, encryption, signatures, independent timestamp authority, provider authentication or network ingestion have been connected. A locally supplied checkpoint can be fabricated and revalidated; replay consistency **does not establish authentic prospective forecasts**. The receipt clock and feed must come from a trusted server and authorized source, with an append-only transactional event store and tamper-evident independent audit, before any forward-performance evidence is published. Do not pass historical archives into this component and label them as live.

Tests: `cd frontend && node --experimental-strip-types --test tests/forward-forecast-ledger.test.ts tests/forward-forecast-journal.test.ts`. Next step: design and test an authenticated server-owned durable event store with idempotent atomic append, startup replay and feed entitlement verification. The PR remains draft until production backup and rollback can be verified; no orders, money, licensed data or production changes were made.

## Prospective issuance cutoff hardening (Loop 5)

The forward-only ledger now rejects **all** newly issued forecast horizons after the first subsequent candle has closed, even when a permissive receipt-lag configuration would otherwise accept an old base candle. For a completed base candle starting at `t` with duration `d`, issuance must occur at a trusted receipt time **strictly before `t + 2d`**. This closes a delayed-feed loophole in which a 3- or 12-bar forecast could previously be recorded after some intermediate outcomes were already observable. Exact retries of an already recorded forecast ID remain idempotent. The forecast record also retains the full provider, venue, source ID, price side and interval so exported records cannot silently lose their feed identity.

Synthetic tests cover issuance immediately before and at the first subsequent close, both longer horizons, idempotent retries and checkpoint replay of forged late issuance. These constraints are necessary for causal research but do not establish source authentication, live forward results or broker profitability.


## Forward-ledger per-horizon score isolation (Loop 5)

The offline prospective ledger and replay-validated journal now expose `summaryByHorizon()` alongside the older combined `summary()`. This returns **independent** issued, pending, settled, void-gap, Brier, log-loss and 50%-reference counts/scores for 1-, 3- and 12-bar horizons. A horizon with no settled predictions reports null losses rather than zero or fabricated skill. Void-gap events are not counted as incorrect predictions. This avoids a misleading combined score where a well-performing short horizon could conceal poor longer-horizon calibration; the older aggregate remains for compatibility and must not be interpreted as per-horizon skill.

These are local, synthetic-code research calculations, **not** authenticated prospective results, independent statistical evidence, tradable signals, live alerts or measured net returns. The independent source feed, durable append-only storage, verified receipt clock and production rollback gate are still missing. Regression tests cover mixed settled/pending horizons, void-gap exclusion, detached result objects and checkpoint restore.
