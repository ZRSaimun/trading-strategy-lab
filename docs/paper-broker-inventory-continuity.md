# Disconnected broker inventory snapshot continuity diagnostic

`inspect_declared_inventory_continuity(expected, previous, current, now_ms)` is a **read-only** offline diagnostic for two caller-declared snapshots of the same account. It calls the existing complete **current** inventory census and additionally checks that a prior checkpoint exists, broker/account identity is stable, snapshot IDs are not reused, sequence advances by exactly one, observation and receipt timestamps advance, adjacent observation timestamps are no farther apart than the declared `max_snapshot_age_ms` freshness window, the prior snapshot's observation-to-receipt lag does not exceed the same declared `max_transport_lag_ms` applied to current evidence, and snapshot deliveries do not overlap. Previous checkpoint metadata and page declarations are bounded and structurally checked. An invalid current census or inconsistent transition returns `HOLD_INVENTORY_CONTINUITY`.

A clean result is **`DECLARED_INVENTORY_CONTINUITY_UNVERIFIED`**. The prior checkpoint is *not* an independently authenticated provider checkpoint; its order/fill contents are not independently verified by this transition function. All timestamps, sequence counters, page-completeness declarations and broker labels are controlled by the caller. This check is not proof of broker snapshot continuity, API support, inventory completeness, terminal status or unknown-order release. It never makes network calls, persists records, reserves risk, or submits orders. `prior_checkpoint_authenticated`, `broker_authenticated`, `inventory_continuity_authenticated`, `may_clear_unknown`, `may_submit_paper_order`, and `may_submit_real_order` remain **false** for every result.

**Conservative quarantine:** A sequence counter advancing by one does not establish uninterrupted inventory coverage if the declared observation timestamps are separated by more than the caller's freshness window. This new observation-gap hold is an offline safety policy, not a documented provider polling guarantee. Real provider feeds may skip sequence numbers, overlap requests, or reuse IDs under documented semantics. Such cases deliberately hold pending authenticated provider-specific reconciliation; do not relax checks or infer eligibility from the label. This is a diagnostic for an assumed one-increment-per-snapshot contract, not a generic live brokerage adapter.

**Production prerequisites:** authenticated, durable and independently anchored broker inventory checkpoints, provider-specific pagination and sequence guarantees, authoritative order/fill/cancel/stop receipts, atomic risk reservations and UNKNOWN attempt reconciliation with the durable ledger. Every real-money order needs secure provider credentials and positive human confirmation for that exact order. No loss limit or profitable outcome is guaranteed. Keep this PR draft until full exact-head CI and independent backup/rollback/production-health gates are proven.

**Prior transport-lag quarantine:** A previous checkpoint with a valid timestamp order can still be too delayed to satisfy the declared transport policy. If `previous.received_at_ms - previous.observed_at_ms > expected.max_transport_lag_ms`, the transition holds with `previous_snapshot_transport_lag`. The exact boundary remains an **unverified** diagnostic, never broker proof or permission to release an UNKNOWN order. The policy is caller-supplied and must be tied to independently verified provider evidence before any execution use.

**Prior order-identity ambiguity:** The previous checkpoint now requires exact broker-order row field names and syntactically valid client/broker order IDs, and checks for repeated client or broker order IDs across all prior pages. Ambiguous identities trigger `HOLD_INVENTORY_CONTINUITY` with `previous_duplicate_order_identity`; malformed prior order row schemas raise `ValueError` (fail closed). This does **not** validate prior fill economics, prior order statuses, or source authenticity. Even a clean result remains unverified and never releases an unknown attempt or permits order submission.
