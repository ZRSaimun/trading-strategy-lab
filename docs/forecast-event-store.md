# Loop 5 — disconnected durable prospective forecast event journal

`backend/app/forecast_event_store.py` is a **server-side, opt-in persistence primitive**, not an active live forecasting system. It uses existing SQLAlchemy `Record` and `Audit` tables without migrations, routes, startup jobs, new services, secrets, vendor calls, broker access, or order execution. It is not imported into the running FastAPI application. The evidence label is deliberately `UNAUTHENTICATED_DISCONNECTED_SERVER_JOURNAL`.

## Data and causality contract

A journal is bound to one immutable exact feed identity: `instrument`, `provider`, `venue`, `sourceId`, `priceSide` (`bid`/`ask`/`mid`), and aligned candle duration in seconds. A separate bounded `maxLagSeconds` is frozen at creation. The caller supplies only a `CANDLE` (`start`, `close`) or `FORECAST` (`id`, `modelVersion`, `horizon` 1/3/12, `probability`, `baseStart`) action. **The store, not the caller, attaches `receivedAt` and `seq`.** The injected clock exists for deterministic tests; a future production worker must use a trustworthy server clock and independently authenticate/authorize its data source before calling this class.

A completed candle is accepted only when its UTC-aligned end is in the past and receipt lag is within the declared bound. Earlier/revised bars and nonfinite/invalid closes fail. A forecast is accepted only after the latest completed candle, before the first subsequent candle closes, with an immutable model/bar/horizon and forecast ID. Settlements are derived on replay **only from subsequently observed completed candles**. A gap voids unresolved forecasts instead of fabricating outcomes. No probability is inferred from market prices here; an external, independently validated model must supply it.

Each append replays the entire bounded journal and uses a compare-and-swap update against the exact previously read database value; a concurrent writer or stale sequence fails closed. The audit row and journal mutation commit in one database transaction, so a failed audit rolls back the event. Restart recovery recomputes outcomes from the event sequence. Duplicate JSON keys, invalid floats, schema drift, sequence gaps, future timestamps, digest mismatches and source changes fail validation. The journal has a hard **5,000-event / 2 MB** bound and intentionally stops rather than truncating its audit history. A SHA-256 checksum detects accidental changes but is **not** a cryptographic signature or protection against an attacker who can rewrite both payload and checksum. Read/write access and backups must be protected separately.

## Verification and limits

Run `cd backend && PYTHONPATH=. pytest -q tests/test_forecast_event_store.py`. The 18 isolated SQLite synthetic tests cover restart settlement, 1/3/12-bar horizons, missing candles, duplicate and stale writers, concurrent writes, clock and feed rejection, tampering, and atomic rollback after a simulated audit failure. PostgreSQL two-connection isolation, schema permissions, backup restoration, real crash recovery and authenticated feed integration still require separate acceptance tests. SQLite success is **not** evidence that those production gates are met.

There is **no live alert transport, paper order fill, broker adapter, authenticated provider, public endpoint, forward accuracy, P&L or drawdown**. Historical BID data cannot be relabelled as prospective market data or executable broker bid/ask quotes. This component must not be merged or deployed solely on synthetic tests. Reconcile the draft Loop 5 branch against current `main`, run full exact-head CI, verify a restorable backup and rollback and post-release health before considering activation. Keep real-money execution disabled.
