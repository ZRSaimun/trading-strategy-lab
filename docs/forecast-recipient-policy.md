# Signed forecast-review recipient policy (offline)

`app.forecast_recipient_policy.audit_forecast_recipient_policy` verifies a **canonical JSON** recipient allowlist bound by domain-separated HMAC-SHA256 to a separately supplied operator verification key. It audits declared forecast-alert claims against the signed policy's UTC validity window and emergency revocations. It returns only aggregate counts, never recipient IDs, keys, claim IDs or message contents.

This is **not** a Telegram integration or permission to send. The caller must independently authenticate the policy issuer, protect the shared secret (minimum 32 random bytes), rotate keys and validate the full claim/outbox population in a transactionally consistent snapshot. A caller that controls both policy and verification key can forge this evidence. HMAC authenticates a shared-secret holder; it does **not** prove that the owner personally authorized a recipient or that Telegram delivered a message.

Policy payload keys: `version: 1`, `audience: "forecast-review-telegram"`, `validFrom`, `validUntil` (Unix UTC seconds, exclusive end, maximum 30 days), `recipients` (unique decimal Telegram chat IDs, 1–100), and `revocations` (unique `{recipientId, at}` entries). Serialize with Python `json.dumps(payload, sort_keys=True, separators=(",", ":"))`. Envelope: `{keyId, payload, signature}` where `signature = HMAC_SHA256(key, b"TradingStrategyLab/forecast-recipient-policy/v1\n" + payload_utf8).hexdigest()`. Keys must be provided out of band; never put production keys or actual chat IDs in source control, logs, documentation examples, or PR comments.

The audit rejects invalid signatures, ambiguous JSON, bad shapes, duplicate claim identities, forged authority claims and malformed timestamps. Claims outside the allowlist or validity window, claims for a recipient revoked by the audit time, and expired/not-yet-effective policies require operator review. It does **not** retroactively declare historical sends invalid; revocation is a conservative present-time review hold. An empty claim population is `NO_CLAIMS`, not evidence of successful delivery. All returned send, retry, paper-order and live-order permissions are false.

To activate actual alerts, independently bind a verified operator-owned policy key to the deployment and recipient consent; use the durable one-attempt claim/outbox workflow, preserve provider response evidence, verify authenticated completed-candle sources and rights, and establish independently reconciled delivery and safe backup/rollback. **No transport, scheduler, route, paper fill or real-money execution is enabled by this change.** Tests use synthetic keys and chat IDs only.
