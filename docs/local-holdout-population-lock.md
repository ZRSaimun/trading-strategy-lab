# Local declared-holdout population overlap lock

This opt-in, offline defense in depth is built on the local SQLite one-attempt registry in PR #151. It prevents *cooperating registrations using the same database* from reusing any declared feed row across different study IDs or candidates. It is not proof of a genuinely untouched holdout, authenticated historical data, a trusted timestamp, or a profitable strategy.

Before the declared holdout begins, construct a valid manifest and its exact chronological census, then call:

```python
from app.local_holdout_population_lock import register_population_locked_holdout

registration = register_population_locked_holdout("/private/holdout.sqlite", manifest, census)
```

This validates the manifest and full census using the declared-only gate, computes a canonical digest of the declared market feed (provider, venue, instrument, quote side and UTC convention), independent of account alias and archive digest, and inserts the study claim, every `(declared feed, row SHA-256)` pair, and every `(declared feed, decision_at_utc)` pair in one `BEGIN IMMEDIATE` SQLite transaction. An identical or *partially overlapping* source population is rejected even when the study ID, candidate, or declared holdout interval changes. Reusing a declared feed decision timestamp is also rejected when the row hash differs, preventing a revised-row representation from silently resetting the same local holdout time slot. A duplicate study is also rejected. Failed inserts roll back all rows and the study claim. To evaluate later, use the existing `audit_declared_holdout_release_once` wrapper; a failed evaluation consumes the single local release attempt.

**Important limits:** The existing `register_local_holdout` function remains available for backward compatibility but **does not reserve population rows**. Registrations made using it, or in another database, are not covered by this overlap lock. Caller-declared feed identities, timestamps and row digests can be falsified or changed; two representations of the same underlying data may still bypass the lock if both their declared row hash and decision timestamp differ. A local database can be restored, edited or replaced, and raw outcomes can be inspected outside this interface. This is an optional local research guard, **not** an independently trusted cross-host registry or a production security boundary. It never reads market archives, contacts a broker, places paper or real orders, or changes production routes.

Synthetic tests cover exact and partial overlap, atomic rollback, duplicate studies, disjoint populations, separate declared feeds, invalid declarations, early registration and concurrent registration. Run from `backend` with `PYTHONPATH=. python -m pytest -q tests/test_local_holdout_population_lock.py`.

**Mixed-mode fail-closed rule:** Once this database has a population-lock table, `register_local_holdout` rejects any new legacy, unreserved registration. If legacy study claims already exist before the first population lock, `register_population_locked_holdout` refuses to activate the lock in that database; it does not silently grandfather or migrate those claims. Use a separate, explicitly managed clean registry for new protected studies, while preserving old records. This prevents the same-database legacy-registration bypass among cooperating callers, but does **not** prevent another SQLite file, direct database tampering, forged row hashes, or direct raw-outcome access. No existing claims or rows are deleted or rewritten.


**Timestamp-lock compatibility (27 October 2026):** This version also creates `holdout_locked_decisions` and atomically reserves one timestamp per declared feed. A previously used **row-only** population-locked database with existing claims cannot be silently upgraded: original censuses are not recoverable from its row-hash reservations, so registration rejects it and preserves the database unchanged. A clean, explicitly managed registry is required for new timestamp-protected studies. Registries already using timestamp locks must have matching nonzero per-study row and timestamp reservation counts; mismatches fail closed. This local integrity check is not tamper resistance or independently authenticated data lineage. Tests include changed-hash/same-time collisions, rollback after partial inserts, incompatible older registries and incomplete reservation counts.

**Declared registration clock consistency (27 October 2026):** A population-locked registration is rejected if the local host clock is earlier than the manifest's declared `registered_at_utc`, even if both are before the holdout starts. Equality is allowed; registration at or after the holdout start remains rejected. The check runs before opening SQLite, so an invalid attempt cannot create a registry or alter an existing claim. This is a consistency check against accidental or opportunistic future-dating, **not** an independently trusted timestamp: the host clock and manifest remain caller-controlled. Synthetic regressions cover both clock boundaries and preservation of an existing database after rejection.

**Release-time reservation integrity (27 October 2026):** The local one-attempt claim path now rechecks a population-locked registry before consuming a holdout release attempt. If one of the row/timestamp reservation tables is missing, a registered study has zero or unequal reservation counts, or either table contains reservations for a nonexistent study, the claim fails and remains unconsumed. A legacy-only database without either population table retains its existing release behavior. This checks local database consistency only: matching counts do not prove that reservations were not substituted, and database restoration, direct outcome access and forged source evidence remain outside the trust boundary. Five synthetic corruption cases cover release refusal without consuming a claim.


**Balanced-reservation corruption hardening (27 October 2026):** Both new registrations and one-attempt releases now reject existing reservations with non-integer decision timestamps, decision timestamps outside their registered study's `[holdout_start_at_utc, holdout_end_at_utc)` interval, or multiple declared source keys across a study's row and decision reservations. New registrations also reject orphaned reservations before adding a study. These checks run within the same SQLite transaction; rejection does not insert a new study or consume a release claim. Four parameterized synthetic regressions cover post-end timestamps, text timestamps, a split declared feed and orphaned rows. Equal row/decision counts alone are insufficient to establish valid lineage. This still cannot authenticate a caller-declared feed, prevent balanced substitution within the same source/time interval, protect against database restoration or guarantee raw outcome secrecy.


**Transactional registration-clock recheck (27 October 2026):** After inserting the complete census reservations but before commit, the writer transaction samples the local clock again. If the clock moved backwards or reached the holdout start, the entire claim and all reservations roll back; otherwise the final sample is stored as the registration time. This prevents stale pre-lock timestamps from allowing late local registration. It does not provide independent timestamp attestation. Synthetic regressions cover a crossed start boundary and a successful registration with a later final timestamp.


**Exact row-to-decision pairing (27 October 2026):** Protected registrations now atomically reserve a third `holdout_locked_pairs` table containing the original declared `(feed, row_sha256, decision_at_utc, study_id)` associations. The release claim checks this table against the frozen manifest census **inside the same writer transaction**, before consuming the one attempt or invoking an outcome loader. Separate matching row and timestamp sets no longer suffice: swapping two row-to-time assignments fails the guarded release. Pair counts and joins to the independent row/time tables are also checked during subsequent registration and release. A populated older row-and-timestamp registry without the original pair table **cannot be silently upgraded**; preserve it unchanged and use a separately managed clean registry for newly protected studies. The synthetic regression suite covers a balanced swap, a missing pair and a pairless older database. This does not independently authenticate the source, timestamp, manifest, local database or external anchor. A direct legacy release without a supplied frozen census cannot prove the original pairing, and a malicious actor controlling both manifest and database can rewrite both.

Registration now rejects any non-table SQLite schema object shadowing the four reserved names (`holdout_claims`, `holdout_locked_rows`, `holdout_locked_decisions`, `holdout_locked_pairs`) before creating claims or reservations. `CREATE TABLE IF NOT EXISTS` alone is not a sufficient type check: an `INSTEAD OF INSERT` trigger on a same-named view can absorb a reservation without preserving the claimed lock. Four synthetic regression cases exercise this failure mode and verify transactional non-registration. This remains a local SQLite integrity check, not independently authenticated holdout evidence.


**Real-table trigger guard (28 October 2026):** A valid SQLite table name and type are insufficient: an `AFTER INSERT` trigger attached to a protected table can silently delete or rewrite the just-inserted claim, row, timestamp or pair while the SQL INSERT succeeds. Registration now rejects *any* trigger attached to the four protected tables within the writer transaction, before inserting a claim or reservation. Four synthetic adversarial cases cover silent deletion on each table and verify no claim/reservations are created. This protects only the cooperating registration path and cannot establish independent provenance, prevent direct database modification, authenticate a market source, or secure a host controlled by an adversary. Existing registries with legitimate custom triggers require independent review and a separately managed clean registry; the guard does not delete or migrate them.
