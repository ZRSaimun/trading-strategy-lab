# Forecast alert/journal reconciliation (Loop 5, disconnected)

`app.forecast_alert_journal_reconciliation.reconcile_forecast_alert_journals` cross-checks a **declared** outbox inventory with replayed prospective forecast issuance events. It runs `audit_forecast_alert_health` first, recomputes derived forecast outcomes using the existing event-journal replay, verifies one journal per declared alert session, and checks each alert's feed identity, issuance sequence, model, horizon, base, timestamp and expiry against the corresponding issuance event. Resolved forecasts with non-cancelled alerts require operator review, even when a simulated provider ACK was recorded.

Input contract: `journals=[{"sessionId": ..., "snapshot": ForecastEventStore.load(...)}]`, `records=[{"sessionId": ..., "state": ForecastAlertOutbox._unpack(...)}]`, `expected_keys=[(session_id, forecast_id), ...]`, `as_of=<trusted UTC epoch seconds>`. Callers must establish a **consistent database snapshot** and independently register the expected population. This function cannot prove the population is complete, protect against concurrent changes between separate reads, or authenticate any source. The existing journal and outbox have no production live-feed authorization.

Fail-closed exceptions indicate missing, extra, duplicate, malformed, forged or inconsistent declared records. The result is always **DECLARED_ONLY**, **NO_DECLARED_ALERTS** or **OPERATOR_REVIEW_REQUIRED**; no status authorizes a notification, paper fill or live order. A cancellation after forecast settlement is not treated as an active alert, but remains historical unverified state. `ACK_RECORDED_UNVERIFIED` never proves recipient/device delivery. No HTTP, scheduling, credentials, database writes or broker integration are added.

Synthetic regression tests cover a healthy linked forecast, empty/missing populations, forged identities/expiry/outcomes, duplicate sessions, settled/voided noncancelled alerts, claimed/ACK states and immutability. Before any operational use: Loop 1 must provide entitled authenticated completed-candle receipts, trusted server clocks, expected-session/candle inventories, exact provider/venue/source/side, and session-aware gap evidence. Loop 5 needs an authorized recipient and a transactionally consistent outbox/journal census plus independently reconciled notification acceptance. Loop 4 owns broker risk gates and execution. BID-only research candles are not executable quotes; no real-money order can be submitted without owner confirmation for that specific order.
