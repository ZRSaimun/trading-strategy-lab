# Offline demo receipt snapshot continuity (Loop 3)

`app.offline_demo_receipt_snapshot_continuity.audit_declared_demo_receipt_snapshot_continuity` is a disconnected, read-only, synthetic-research helper. It compares two **full caller-declared** snapshots of one demo order. It calls the merged single-snapshot receipt replay for **both** populations rather than trusting their summaries. A later snapshot must advance `as_of_ms`, retain all immutable source/account/instrument/order/intent fields, preserve every earlier unique receipt byte-for-byte as a prefix, and only add receipts first received **after** the previous snapshot cutoff. Exact duplicate deliveries remain idempotent. The current manifest must not predate the previous one.

A backfilled receipt with a `received_at_ms` at or before the previous cutoff is **not** silently accepted: the caller must stop and reconcile the discrepancy externally. Rewriting old receipts and recomputing all self-declared hashes also fails if the original full snapshot is supplied unchanged. However, a coordinated rewrite of *both* snapshots is not detectable without an independently retained trusted checkpoint. The emitted SHA-256 checkpoint is not a broker signature, durable journal, or externally timestamped precommitment. A complete declared receipt sequence can still omit actual broker fills.

Example (synthetic): a first snapshot declares submission, acceptance, and 2/5 filled contracts. A second snapshot retains those events and appends one more fill of 1 contract received after the first cutoff. The result reports **3/5 declared fills**, **2 remaining**, and **1 new declared receipt**, while requiring manual broker reconciliation. It never authorizes paper or real orders.

Tests: `cd backend && PYTHONPATH=. python -m pytest -q tests/test_offline_demo_receipt_snapshot_continuity.py`. No provider connections, paid APIs, database writes, archive publication, order senders, migrations, or production routes are added. These checks are *not* crash recovery, durable idempotency, broker-state verification, proof of untouched holdouts, multi-year net-of-cost performance, or evidence of profit. Any production rollout requires owner-confirmed target, backup restoration, rollback, and health checks; no operational activation is required for this disconnected helper.
