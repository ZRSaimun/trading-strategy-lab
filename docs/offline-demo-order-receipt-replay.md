# Disconnected demo order receipt replay (Loop 3)

`app.offline_demo_order_receipt_replay` validates a **caller-declared**, bounded order-event history for a single whole-contract BUY/SELL order. It is an isolated pure-Python research helper, not a persistent journal, broker integration, trading endpoint, or broker-account reconciliation. It cannot send, cancel, or authorize demo/live orders. All outcomes explicitly set `may_execute_demo_order=False` and `may_execute_real_order=False` and require manual broker reconciliation.

The caller supplies a strict provider/venue/account/instrument/client-order identity, a previously computed intent digest, a chronological sequence of `SUBMITTED`, `ACCEPTED`, `FILL`, `CANCEL_REQUESTED`, `CANCELED`, `REJECTED`, and `EXPIRED` events, and a declared event-count/head-digest manifest. Every event binds the intent digest and previous event fingerprint, as well as a caller-declared receipt digest. Identical repeated deliveries are idempotently ignored; conflicting retries, missing sequence numbers, changed hashes, source/account/order mismatches, quantity overfills, invalid lifecycle transitions, and late/out-of-order events fail closed. A cancel request does not cancel prior or intervening partial fills. Rejections, expiries and cancellations **never prove zero actual broker exposure**. Unknown outcomes remain explicitly unknown.

**Threat model:** SHA-256 chains detect *inconsistency relative to a retained independent reference*, not deliberate coordinated rewrites. The caller supplies the manifest and receipt hashes; neither is cryptographically signed by a broker nor independently preregistered. A complete declared population can omit actual fills or delayed receipts. A replay after a crash is deterministic if the caller persists the exact validated inputs, but this helper does **not** provide transactional storage, atomic write-ahead logging, multi-process locking, exactly-once broker submission, signed statement provenance, broker recovery, live executable quotes, partial-cancel acknowledgment, margin checks, financing, FX, or P&L. A future operational adapter must first establish authenticated read-only broker snapshots, a supported documented demo API, durable idempotency, broker-specific order-state transitions, secure credentials and owner-approved policy. Trading 212 CFD API actions are not assumed to exist.

Run isolated synthetic tests: `cd backend && PYTHONPATH=. python -m pytest -q tests/test_offline_demo_order_receipt_replay.py`. No historical or licensed archives are included. Tests show invariants and error handling, **not** independently validated multi-year net-of-cost performance, untouched holdouts, queue position, real fills or profitable trading. Merge only after exact-head full CI and fresh conflict review. No production deployment without owner-confirmed target, restorable backup, rollback and health verification; this disconnected helper requires no operational activation.
